# READMEを書く

READMEは、初めての人が使い始めるための入口であり、取扱説明書ではない。
任意の機能の手順やリファレンスまで載せると、使い始めるのに要る数行がその中に埋もれる。
この手順は、READMEに置く内容を絞り、それ以外を別のファイルに移してリンクする。分量は予算で抑え、スクリプトで計る。

## 守ること

- 内容は消さずに移す。消してよいのは、誤り（実態と合わない説明を含む）、古い内容、ほかの文書やREADMEの中の表と重なる内容だけで、消したものは報告に書く
- 既存のREADMEを書き換える前に、節ごとの扱い（残す・縮める・移す・消す）と移す先の表を見せて、了承を得る。ファイルを新しく作るのも、この表に含める
- 予算に収まっているREADMEは、節を移したり、まとめたり、節の順を変えたりしない。見直しを頼まれても、直すのは次の5つだけにする。それ以外の、読みやすさのための組み替えの案は、報告に提案として書く
  - 誤り（実装や実態と食い違う記述。当てはまるものが無い場合分けや、無いファイルへの言及を含む）
  - 古い内容（切れたリンク、古いURL）
  - `japanese-tech-writing`の「見出しと用語の逐語訳」と「手順の書き方」に反する箇所。直すのはその節の中だけで、見出しの言い換えと、節の中の項目の並べ替え、分割はしてよい
  - 体言止めになっていない箇条書きと番号付きの手順、書き方のそろっていない表のセル、ファイルへのリンクの無い表のセル（「書き方の規則」）
  - 同じREADMEの表と重なる、表の外の説明（「書き方の規則」）
- ただし、次の2つは、予算に収まっていても行う（「READMEに置くこと」）
  - 開発者向けの節の、`docs/development.md`への移動
  - 別々の章に分かれた、関連する節の1つの章へのまとめ
- マーカーで囲んだ自動生成のブロック（`<!-- 〜:begin -->`から`<!-- 〜:end -->`まで）は、手で直さない。直すべき内容は、生成元のスクリプトや設定を直す案として報告に書く
- 頼まれていないコードやテストのファイルを足さない。足すとよいもの（Exampleの関数など）は、提案として報告に書く
- READMEに書くコマンド、フラグ、パス、設定の名前は、実装（フラグの定義、`-h`の出力、設定を読む処理）と照らし合わせる。場合分け（「〜していないものは」）とファイルの有無も、実態と照らし合わせる。確かめられないことは書かない
- 段落の文体（です・ます調、である調）と言語は、既存のREADMEに合わせる。新しく書くときは、リポジトリのほかの文書に合わせ、無ければ会話の言語で書く。箇条書き、番号付きの手順、表のセルは、文体によらず体言止めにする（「書き方の規則」）
- 安全に関わる注意（データを消す操作、外部に公開する設定、秘密情報の扱い）は、説明を移しても、要約の1行をREADMEに残す

## READMEに置くこと

1. 何か：1〜3文。何をするもので、何が楽になるか
2. 入れ方：主な入れ方を1〜3通り
3. 最初の使い方：必須の設定と、最小の例
4. 詳しい情報の場所：docs/、APIの文書、`-h`の出力、文書のサイト
5. ライセンスと作者

それ以外は、[references/placement.md](references/placement.md)の表に従って移す。
開発者向けの内容（開発の決まり、変更の手順、リリースの手順）は、利用者が使い始めるのに要らないので、予算に収まっていてもREADMEに置かない。`docs/development.md`（リポジトリに`CONTRIBUTING.md`があればそちら）に移し、READMEの「開発」の節には、そのリンクを1行だけ置く。
関連する事項は、1つの章（`##`の見出し）にまとめる。ある作業の別のやり方、続き、補足（バージョンを指定したインストール、更新、アンインストールなど）は、別の章にせず、その作業の章の中の節（`###`）にする。たとえば「バージョンを指定したインストール」は、「インストール」の章の中の節にする。まとめるときは節の中身を変えず、見出しの深さと置き場所だけを変える。これも、予算に収まっていても行う。
種類ごとの構成は次のとおりで、雛形は[references/templates.md](references/templates.md)にある。

| 種類 | 構成 |
|---|---|
| CLIツール | 説明 → Install → Setup（必須の設定だけ）→ Usage → Documentation → License・Author |
| ライブラリ | 説明 → Install → 最小の例を1つ → Documentation（APIの文書と、ほかの例の場所）→ License |
| アプリ・サービス | 説明 → Quick start（5手順以内）→ Documentation → 開発（リンクだけ）→ License |

書き方の規則は次のとおり。

- 使い方は、1つの作業につき見出し（または1文）と1つのコマンドにする
- 日本語のREADMEの箇条書き、番号付きの手順、表のセルは、体言止めにする。コミットメッセージやプルリクエストの本文（`git-commit`のSkillの書式）と同じ規則で、段落の文には当てはめない。例：「`node scripts/sync-skills.mjs`を実行する」ではなく「`node scripts/sync-skills.mjs`の実行」、「`gh skill update`の対象から外れる」ではなく「`gh skill update`の対象外」
- 表のセルは、末尾に句点を付けず、同じ列のセルの形をそろえる（`japanese-tech-writing`の「表のセルの書き方」）。例：「Node.js 18以降が要る。」ではなく「Node.js 18以降が必要」
- 表のセルで、リポジトリの中のファイル（ライセンスの本文など）を示すときは、そのファイルへのリンクにする。ライセンスの列には、ライセンスの名前と本文のファイルへのリンクを置く（`[MIT](LICENSE)`、`Unlicense（[LICENSE.txt](<name>/LICENSE.txt)）`）
- 表に書いた内容を、表の外の段落や別の節で繰り返さない。重なる説明は消し、表に無いことだけを残す。例：一覧の表のライセンスの列に書いたライセンスを、ライセンスの節で説明し直さない
- 複数の操作からなる作業（セットアップ、開発、リリース）は、行う順の番号付きの手順にし、必須と任意、決まりと手順を分ける（`japanese-tech-writing`の「手順の書き方」）。英語のREADMEにも当てはめる
- 段落は3文以内にする。作った理由や背景は2文までにする
- 任意の機能は、READMEには1行の説明とリンクだけを置く
- オプションの一覧は、`-h`の出力を写すか、docs/に移す
- 機能の一覧は、使い始める判断に要るものだけにする（目安は5項目）
- バッジは、状態を示すもの（CI、版、APIの文書）だけにする

## 予算

| 段階 | 当てはまるもの | 全体の上限 |
|---|---|---|
| small | 主なコマンドが1つか、小さなライブラリで、必須の設定が無い | 120行 |
| standard（既定） | ほかに当てはまらない | 200行 |
| large | 使い始めるのに要るコマンドや手順が多く、別に文書のサイトも無い | 300行 |

- 地の文は全体の上限の30%まで、使い方以外の1つの節も30%まで。見出しはH3まで。コードブロックは1つ15行まで（`-h`の出力の写しを除く）
- 地の文の表示幅（全角は2桁）の合計は、地の文の上限×80桁まで。日本語の文を1行に長く書いても、行数だけでは見逃さないためである
- 任意の機能やメンテナンス用のコマンドが多いことは、段階を上げる理由にしない。それらは移す対象である

予算は、次の順で決める（上ほど優先）。

1. 会話での開発者の指示（「300行まででよい」「検索構文はREADMEに残したい」など）。スクリプトのオプションで渡す
2. READMEと同じディレクトリの設定ファイル`.readme-budget.json`
3. 規模からの提案。リポジトリを見て段階を選び、理由を添えて示す
4. 既定値（standard、200行）

開発者の指示を続けて使うなら、設定ファイルに書くかを尋ねる。段階の判断の基準と、設定ファイルの書き方は[references/budget.md](references/budget.md)にある。
予算を超えたまま終えるときは、超えた理由を報告に書く。

## 言語ごとの節

入れ方、APIの文書の場所、例の置き場所などは言語で変わる。言語ごとの節を`references/lang/<言語>.md`に置き、選んだ言語の節だけを読む。今あるのは[Go](references/lang/go.md)だけである。

言語は、実装の言語ではなく、利用者が触れる言語で選ぶ。

- CLI・アプリ：実装の言語の節を読み、入れ方は配布の方法（リリースのバイナリ、Homebrewなど）を先に書く
- ライブラリ：公開しているAPIの言語の節を読む（Rustで書いてPythonのバインディングを配るなら、Python）
- 複数の言語があるとき：利用者が入れるものの言語の節を読む

節の無い言語では、この手順の共通の部分で進め、その言語の慣例（パッケージの入れ方、APIの文書と例の置き場所）を調べて当てはめる。そうしたことは報告に書く。

## 手順

### 1. リポジトリを調べる

- 種類（CLI、ライブラリ、アプリ）と言語を決め、言語の節を読む
- 入れ方、必須の設定、主なコマンドを、実装とビルドの設定（リリースの設定、パッケージの定義）から確かめる
- 既存の文書を確かめる：`docs/`、`CONTRIBUTING.md`、`SECURITY.md`、`CHANGELOG.md`、文書のサイト、READMEを参照しているファイル（READMEの節へのリンクは、移すと切れる）
- `.readme-budget.json`があれば読む

### 2. 計る

```bash
node "${CLAUDE_SKILL_DIR}/scripts/readme_stats.mjs" README.md
```

`${CLAUDE_SKILL_DIR}`はこのSKILL.mdのあるディレクトリを指す。Claude Code以外で展開されないときは、そのディレクトリのパスに置き換える。

全体・地の文・節ごとの行数、見出しの深さ、長い節、リンクの切れを、予算とその出どころ（既定、設定ファイル、オプション）とともに出す。日本語の箇条書き、番号付きの手順、表のセルが体言止めでないときと、表のセルの末尾に句点があるときも指摘する（自動生成のブロックとコードブロックは見ない）。ほかの節の見出しを含む見出しの節（「インストール」と「バージョンを指定したインストール」など）は、同じ話題の節として「注意」に出す。
開発者の指示は`--preset large`、`--max-lines 250`のようにオプションで渡す。オプションの一覧は`--help`で出る。
指摘があれば終了コード1で終わる。長いコードブロックは「注意」として示すだけで、`-h`の出力の写しなら残してよい。同じ話題の節の「注意」が出たら、節の中身を読み、同じ話題なら1つの章にまとめる（「READMEに置くこと」）。

READMEが無いとき（新しく書くとき）は、この手順を飛ばす。

### 3. 予算を決める

「予算」の節の順で決め、段階を選んだ理由を1〜2文で示す。

### 4. 扱いを決めて、了承を得る

既存のREADMEを書き換えるときは、節ごとの扱いを表にして見せ、了承を得てから書く。

| 節 | 行数 | 扱い | 移す先 |
|---|---|---|---|
| セットアップ > OCR | 68 | 移す | `docs/ocr.md` |
| 検索構文 | 100 | 残す（開発者の指示） | — |

手順2で予算の超過が無かったREADMEでは、表に「移す」「縮める」を書かない。開発者向けの節を`docs/development.md`に移すことと、関連する節を1つの章にまとめること、「守ること」の5つ（誤り、古い内容、見出しと手順の書き方、体言止めと表のセルの書き方、表と重なる説明）の直す箇所だけを示し、直す箇所が無ければ、そう伝える。

### 5. 書く

- 移す先のファイルは、単独で読めるようにする。冒頭に何の文書かを1文で書き、見出しの階層を直し、相対リンクを移した先から見たパスに直す
- 移した先の一覧を、READMEのDocumentationの節に置く
- READMEの節を参照していたファイル（ほかの文書、コードのコメント）のリンクを、移した先に付け替える
- 日本語の文章は、`japanese-tech-writing`のSkillが入っていれば、その規範で点検し、そのSkillの`scripts/fix_spacing.mjs`で日本語と英数字の間の空白を除く。`--fix`が自動生成のブロックの中を変えたら、その変更は戻す（ブロックの中身は生成元で決まる）。入っていなくても、次の2点は確かめる
  - 見出しと用語が、英語の用語を語ごとに訳した造語（version pinningの「版の固定」など）になっていないか。その場面で慣用される語（インストールなら「バージョン」）と動詞（タグなら、作る側は「付ける」、使う側は「指定する」）で書く
  - 手順が、行う順の番号付きの箇条書きで、必須と任意、決まりと手順が分かれ、条件が項目の先頭にあるか

### 6. 確かめる

書き換える前のREADMEを一時ファイルに取り出し（`git show HEAD:README.md > <一時ファイル>`）、移した先と一緒に計る。

```bash
node "${CLAUDE_SKILL_DIR}/scripts/readme_stats.mjs" --moved-from <一時ファイル> README.md docs/*.md CONTRIBUTING.md
```

READMEの後ろには、内容を移した先と、READMEと内容が重なるとして消した部分の残る先（`THIRD-PARTY-NOTICES.md`など）を、すべて並べる。並べないファイルの中身は「どこにも無い」と出る。

- 予算の超過とリンクの切れを直す。移した先のファイルのリンクも確かめる
- 「どこにも無い」と出たコードブロック、インラインコード、URLが、消すと決めたものだけかを確かめる。違えば戻す
- 見出しの「どこにも無い」は、名前を変えたものなら問題ない

新しく書いたときは、`--moved-from`を付けずにREADMEを計る。

### 7. 報告する

次のことを短く書く。

- 前後の数値（全体、地の文の行数）と、使った予算とその出どころ
- 移したものと移す先、消したものとその理由
- 確かめられなかったこと（実装と照らし合わせられなかった記述など）

## 見直しだけを頼まれたとき

手順1〜3を行い、指摘と直す案を示す。予算に収まっていても、開発者向けの節がREADMEにあること、関連する節が別々の章に分かれていること、「守ること」の5つ（誤り、古い内容、見出しと手順の書き方、体言止めと表のセルの書き方、表と重なる説明）は指摘に含める。ファイルは変えない。
