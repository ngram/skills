# リポジトリの個人情報・機微情報の確認

リポジトリと、そこから公開したパッケージに、個人情報・秘密情報・機微情報が含まれていないかを調べて報告する。

今のファイルを調べるだけでは足りない。
消したり直したりした内容は過去のコミットに残り、GitHubではマージ後に消したブランチの内容もPRの参照（`refs/pull/*`）から辿れる。
コミットメッセージと作成者の名前・メールアドレスはファイルの外にあり、公開済みのパッケージはリポジトリを直しても変わらない別のコピーである。
この手順は、これらを順に調べる。

## 守ること

- 読み取りだけを行う。履歴の書き換え、強制push、タグの付け替え、リポジトリの削除・改名・公開範囲の変更、パッケージの取り下げは、手順とスクリプトを渡してユーザーが実行する。どれも元に戻せないか、他人の手元のクローンや公開済みのリンクに影響し、行うかどうかはリポジトリの持ち主が決めることだからである
- 見つけた値を書き写さない。報告、プルリクエスト、issue、コミットメッセージには「個人のメールアドレス」「GitHubのトークン」のように種類と場所だけを書く。公開の場に値を書けば、それ自体が新しい漏えいになる
- 秘密情報やワンタイムパスワードをチャットに貼ってもらわない。探したい語（実名など）は、ユーザーがリポジトリの外のファイルに書き、`--terms-file`でスクリプトに渡せる
- 調べられなかった範囲を、調べたように書かない。報告に「調べられなかった範囲」として残す

## 手順

### 1. 調べる対象をそろえる

作業用のクローンを、すべての参照を含む形で用意する。

- GitHubのリポジトリは`git clone --mirror <URL> <作業ディレクトリ>`で取る。ブランチとタグに加えて、`refs/pull/*`（PRの参照）も入る
- 既存のクローンを使うときは、次を確かめる
  - `git remote -v`の取得先が、調べたいリポジトリか。改名したリポジトリや、作り直した環境のクローンでは、古いURLのままのことがある
  - `git rev-parse --is-shallow-repository`が`true`なら、浅いクローンで古い履歴が無い。`git fetch --unshallow`で取り直す
  - PRの参照は`git fetch origin '+refs/pull/*:refs/remotes/origin/pull/*'`で取る
- 公開済みのパッケージがあるかを、`*.gemspec`、`package.json`（`private`が`true`でないか）、`pyproject.toml`、`Cargo.toml`などから確かめる

ネットワークの制限でミラーを取れないときは、手元のクローンで調べ、取れなかった参照を報告に書く。

### 2. 探す語を集める

スクリプトは一般的な形（トークン、メールアドレス、電話番号など）を探す。プロジェクトと持ち主に固有の語は、次の2つから集めて渡す。

- リポジトリの決まり：`CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING.md`などに「書かない」「入れない」とある内容。例えば「コミットにモデル名を書かない」なら`--pattern 'Claude (Opus|Sonnet|Haiku)'`にする
- 持ち主だけが知っている語：実名、個人のメールアドレス、家族の名前、住所、勤務先、社内のプロジェクト名。チャットに書かずに済むよう、リポジトリの外のファイルに1行1語で書いてもらい、`--terms-file`で渡す

法的な見解、第三者への評価、社内のやりとりのように、語では探せない内容がありそうなら、手順4で文章を読む。

### 3. スクリプトで検査する

```bash
node "${CLAUDE_SKILL_DIR}/scripts/scan.mjs" --repo <作業ディレクトリ> --terms-file <語のファイル> --pattern '<正規表現>'
```

`${CLAUDE_SKILL_DIR}`はこのSKILL.mdのあるディレクトリを指す。Claude Code以外で展開されないときは、そのディレクトリのパスに置き換える。

スクリプトは、すべての参照から辿れるファイルの全版、コミットと注釈付きタグのメッセージ、作成者・コミッター・タグの作成者、過去に追加されたファイルの名前（`.env`、鍵のファイルなど）を調べる。
見つかった値は、先頭の数文字と長さだけを出して伏せる。それぞれに、今の`HEAD`にあるか、最初に入ったコミット、そのコミットを含む参照（PRの参照だけから辿れるかどうか）を添える。
見つかったものがあれば終了コード1で終わる。

- 自動生成のファイルや取り込んだ外部のコード（型定義、`vendor/`、ロックファイル）が一致を埋めるときは、`--exclude '<パスの正規表現>'`で外す。外したパスは報告に書く
- `--show`は値を伏せずに出す。チャットの記録に値が残るので、ユーザーが求めたときだけ使う
- オプションの一覧は`node "${CLAUDE_SKILL_DIR}/scripts/scan.mjs" --help`で出る

### 4. 一致した箇所を読んで判定する

一致を機械的に問題とせず、前後を読んで判定する。

- ファイルの一致は`git show <blob> | sed -n '<行>p'`（PowerShellでは`(git show <blob>)[<行>-1]`）、メッセージの一致は`git show -s <コミット>`で開く。開いた値はチャットの記録に残るので、判定に必要な箇所だけを開く
- 規則ごとの誤検知の例と判定の目安は[references/patterns.md](references/patterns.md)にある
- コミットメッセージは、件数が多くなければすべて読む（`git log --all --format='%h %an%n%B'`）。語で探せない内容（法的な見解、第三者への評価、社内の事情、ツールが自動で付けた行）はここで見つかる
- 消されたファイルの一覧（`git log --all --diff-filter=D --name-only --format='%h'`）も見る。誰かが消すと決めた内容は、残してはいけないものであることが多い
- 画像、PDF、Officeの文書はスクリプトが中身を見ない。スクリーンショットに写った個人情報、写真のEXIFの位置情報、文書のプロパティの作成者名がありうるので、ファイルの一覧から該当するものを拾って確かめる

判定した結果には、重要度と見える範囲を付ける。

| 重要度 | 目安 |
| --- | --- |
| 高 | 使える秘密情報（トークン、パスワード、秘密鍵）、個人の連絡先（個人のメールアドレス、電話番号、住所）、ハンドル名で活動している人の実名 |
| 中 | 所属を示すメールアドレス、公開のIPアドレス、内部のホスト名、ユーザー名入りのパス、プロジェクトの決まりに反する内容 |
| 低 | 開発用のURL、プライベートのIPアドレス、ツールが自動で付けた行、OSが作るファイル |

見える範囲は、「今のファイル」「履歴だけ」「PRの参照だけ」「公開済みのパッケージ」のどれか（複数可）である。

### 5. 公開済みのパッケージを調べる

公開済みの版は、リポジトリを直しても変わらない。版ごとに取得し、新しい空のディレクトリに展開して`--dir`で検査する。
取得には、インストールやビルドをせず、パッケージのコードを実行しない方法を使う。

| レジストリ | 版の一覧 | 取得と展開 |
| --- | --- | --- |
| RubyGems | `gem list <名前> --remote --all --exact` | `gem fetch <名前> -v <版>`、`gem unpack <ファイル>.gem --target <ディレクトリ>`。メタデータ（作成者、メールアドレス）は`gem spec <ファイル>.gem`で出し、展開先に保存してから検査する |
| npm | `npm view <名前> versions` | `npm pack <名前>@<版>`で得た`.tgz`を`tar -xzf`で展開する。作成者は`npm view <名前>@<版> author maintainers` |
| PyPI | `https://pypi.org/pypi/<名前>/json` | `https://pypi.org/pypi/<名前>/<版>/json`の`urls`にある配布物を取得して展開する。`pip download`は、ソース配布物のビルドでコードを実行することがある |

取り下げ（yank）済みの版は取得できないことが多い。取得できなかった版は報告に書く。

### 6. gitの外に残る情報を確かめる

GitHubなどのホスティングサービスには、gitの履歴とは別に次の情報が残る。GitHubのMCPサーバーか`gh`コマンドが使えれば一覧を取り、使えなければユーザーに確かめてもらう項目として報告に書く。

- PRとissueの本文・コメント・レビューコメント、Releaseの説明と添付ファイル、Actionsのログと成果物、Discussions
- Wiki（別のリポジトリ`<名前>.wiki.git`。`git clone --mirror`で取ってスクリプトで検査できる）
- リポジトリの説明（About）、トピック、ホームページのURL
- フォーク。公開リポジトリを非公開にすると、公開のフォークは切り離されて公開のまま残る

外部のアーカイブ（Software Heritage、検索エンジンのキャッシュ、パッケージのミラー）と他人の手元のクローンは調べられない。どの参照からも辿れなくなったコミットも、GitHubではSHAを指定すると表示されることがある。

### 7. 報告する

次の形で報告する。値は書かず、種類と場所で示す。

```markdown
## 結果
高 N件、中 N件、低 N件。<最も重い1件を一文で>

## 見つかったもの
| 重要度 | 種類 | 場所 | 見える範囲 | 判断 |
| --- | --- | --- | --- | --- |
| 高 | 個人のメールアドレス | `<パス>`の9行目（コミット`<SHA>`から） | 履歴だけ、公開済みの<パッケージ> 0.1.0 | 対処が必要 |

## 問題がなかったもの
- <調べた種類>：該当なし

## 誤検知として除いたもの
- <種類>（<場所>）：<理由>

## 調べられなかった範囲
- <範囲>：<理由>

## 対処の選択肢
<見つかったものに合う選択肢だけ>
```

### 8. 対処を選んでもらう

対処の選択肢と、それぞれの注意点は[references/remediation.md](references/remediation.md)にある。見つかったものに合うものだけを示し、どれを行うかはユーザーに決めてもらう。

- 使える秘密情報が漏れていたら、何より先に無効化と再発行を勧める。履歴から消しても、すでに複製された値は取り消せない
- 次に、今のファイルを直して新しい版を出す。履歴の書き換えとGitHubに残る参照への対処は、その後で必要かどうかを決める
- 履歴を書き換える手順は、スクリプトと確認の手順として渡し、ユーザーの手元で実行してもらう。ユーザーがWindowsなら、PowerShellかコマンドプロンプトで動く形で渡す（Pythonは`py`、正規表現の`^`や`|`の引用）
