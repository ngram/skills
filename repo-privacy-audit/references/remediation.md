# 対処の選択肢と注意点

見つかったものに合う選択肢だけをユーザーに示す。どれも、ユーザーが自分の手元で実行するものである。
APIキー、ワンタイムパスワード、リポジトリの管理者の操作が要るので、エージェントの環境から代わりに実行することは勧めない。

## 1. 秘密情報を無効化して再発行する

使える秘密情報（トークン、パスワード、秘密鍵）が見つかったら、ほかの対処より先に行う。
一度公開した値は、複製や記録が残っている可能性があり、履歴から消しても取り消せないからである。

- 発行元のサービスで無効化し、新しい値を発行する。発行元に監査ログがあれば、漏れていた期間に使われていないかを確かめる
- GitHubのsecret scanningは、一部のサービスのトークンを検出すると発行元に通知し、自動で無効化されることがある
- 無効化した値が履歴に残っていても、それ自体はもう使えない。履歴の書き換えは、次の節の理由が別にあるときに行えばよい

## 2. 今のファイルを直して新しい版を出す

- ファイルを直してコミットし、パッケージなら新しい版を公開する
- 公開済みの古い版は、そのまま取得できる。取り下げはレジストリごとに条件が違う
  - RubyGems：`gem yank <名前> -v <版>`。`yank_rubygem`の権限を持つAPIキーが要り、MFAを有効にしていればワンタイムパスワードも求められる。Trusted Publishingで発行されるキーでは取り下げられない。取り下げた版の番号は再利用できない
  - npm：`npm unpublish <名前>@<版>`は、公開から72時間以内か、依存されておらず、ダウンロードが少なく、持ち主が1人であるなどの条件を満たすときだけ使える。満たさないときは`npm deprecate`で警告を出すことしかできず、中身は残る
  - PyPI：yankしても、版を`==`で指定したインストールでは取得できる。中身を消すには、Webの画面からリリースかファイルを削除する。削除したファイル名は再利用できない
- 取り下げに使うAPIキーとワンタイムパスワードは、チャットに貼らずにユーザーの端末で入力してもらう

## 3. 履歴を書き換える

過去の版に個人情報が残っていて、持ち主が消したいときに行う。[git-filter-repo](https://github.com/newren/git-filter-repo)を使う（`pip install git-filter-repo`、Windowsでは`py -m pip install git-filter-repo`）。

### 手順

1. 控えを取る：`git clone --mirror <URL> backup.git`。消したい内容がそのまま入っているので、公開の場所に置かず、作業が終わったら消す
2. 作業用のミラーを別に取る：`git clone --mirror <URL> work.git`。filter-repoは、取り直したばかりのクローンでなければ書き換えを拒む
3. PRの参照を消す：`git for-each-ref --format='delete %(refname)' refs/pull | git update-ref --stdin`。GitHubは`refs/pull/*`へのpushを受け付けないので、残すとpushで失敗する
4. 書き換える。目的ごとのオプションは次のとおり
   - ファイルの中の文字列を置き換える：`git filter-repo --replace-text <式のファイル>`（1行に`消す文字列==>置き換える文字列`、正規表現は`regex:`を前に付ける）
   - コミットメッセージの文字列を置き換える：`--replace-message <式のファイル>`（書き方は同じ）
   - 作成者の名前とメールアドレスを置き換える：`--mailmap <ファイル>`（1行に`新しい名前 <新しいアドレス> 古い名前 <古いアドレス>`）。注釈付きタグの作成者も置き換わる
   - ファイルを全履歴から消す：`--invert-paths --path <パス>`
   - 特定の版のファイルや、特定のコミットのメッセージだけを差し替える：Pythonで`import git_filter_repo as fr`とし、`fr.RepoFilter(args, blob_callback=..., commit_callback=...).run()`に関数を渡す。`blob.original_id`と`commit.original_id`で対象を選べる
   - 中身が変わらなくなったコミットは、既定で取り除かれる
5. pushする前に確かめる
   - 同じ語を渡して`scan.mjs --repo work.git`を実行し、対象が見つからないこと
   - 最新のファイルが意図どおりであること（`git -C backup.git rev-parse HEAD^{tree}`と`git -C work.git rev-parse HEAD^{tree}`が一致するか、違うなら`git diff`で差分が意図どおりか）
   - コミットの件数、タグの指す先、タグの作成者
   - 消したかったコミットが無いこと（`git -C work.git cat-file -e <古いSHA>`が失敗する）
6. タグのpushで動くワークフロー（パッケージの公開など）があれば、先に無効にする。書き換えたタグをpushすると、公開がもう一度走る
7. pushする：filter-repoは書き換えのあとに`origin`のリモートを外すので、`git remote add origin <URL>`で付け直し、`git push --force origin 'refs/heads/*:refs/heads/*' 'refs/tags/*:refs/tags/*'`で送る。無効にしたワークフローを戻す
8. 共同作業者に、手元のクローンを取り直してもらう。古いクローンからpushやマージをすると、古いコミットが戻る

### 書き換えだけでは消えないもの

強制pushしても、GitHub上の古いコミットはすぐには消えない。

- PRの参照（`refs/pull/*`）は読み取り専用で、利用者は消せない。PRそのものも削除できない
- どの参照からも辿れなくなったコミットも、SHAを指定すると表示されることがある
- フォークは別のリポジトリとして、古い履歴を持ち続ける

これらには次の節で対処する。

## 4. GitHubに残る参照への対処

| 方法 | 結果 | 注意点 |
| --- | --- | --- |
| GitHubサポートに依頼する | PRの参照とキャッシュされた表示を消してもらえる | GitHubのドキュメントでは、秘密情報を無効化しても危険が残る場合（個人情報など）に限って対応するとしている。依頼の前に、履歴の書き換えと強制pushを済ませておく |
| 改名して非公開にし、同じ名前で作り直す | 古いPRの参照とコミットは、非公開のリポジトリの中に残り、外からは見えなくなる。控えも兼ねる | issue、PR、スター、Release、設定は引き継がれない（次の節） |
| 削除する | PR、issue、参照がまとめて消える | 元に戻せない（条件によっては90日以内に復元できる）。削除の扱いと名前の再利用の条件は、実行する前にGitHubのドキュメントで確かめる |
| PRをアーカイブする | PRのページが隠れる | gitの参照まで隠れるかは確かめられていない |

フォークの古い履歴は、フォークの持ち主に消してもらうしかない。公開リポジトリを非公開にすると、公開のフォークは切り離されて公開のまま残る。

## 5. 作り直しや書き換えに伴う影響

対処を選んでもらうときに、該当するものを添える。

- パッケージの来歴の証明（Sigstoreの証明、npmのprovenance）は、公開したときのコミットとワークフローの実行を指す。履歴を書き換えると、そのリンクが切れる。パッケージそのものは影響を受けない
- タグを付け直してpushすると、タグで動くワークフローがまた走る
- 作り直したリポジトリは新しいリポジトリIDを持つ。リポジトリを選んで許可する設定（GitHub Appのインストール先、Codespacesのシークレット）は選び直す。Actionsのシークレット、Webhook、デプロイキー、ブランチの保護も設定し直す
- Trusted Publishingは、レジストリによって照合する項目（所有者、リポジトリ名、ワークフローのファイル名、リポジトリID）が違う。次の公開で通るかを確かめる
- 改名や作り直しで、旧名からの転送が無くなる。古いリンクは404になる
- issueとPRの番号は1から振り直しになり、古い番号へのリンクは別のものを指すか404になる
- 手元のクローン、CIのキャッシュ、書き換えに使った控えには、古い履歴が残る。取り直すか消す

## 6. 再発を防ぐ

- gitの`user.name`をハンドル名に、`user.email`をGitHubのnoreplyのアドレス（`<ID>+<ユーザー名>@users.noreply.github.com`）にする。GitHubの設定で、メールアドレスを含むpushを拒否できる
- パッケージのメタデータ（gemspecの`email`、`package.json`の`author`）に個人のアドレスを書かない。省くか、noreplyのアドレスにする
- `.gitignore`に`.env`と鍵のファイルを入れ、見本は`.env.example`として置く
- リポジトリの決まり（コミットに書かないもの、置かないファイル）を`CLAUDE.md`や`CONTRIBUTING.md`に書く
- GitHubのsecret scanningとpush protectionを有効にする。手元ではgitleaksなどをコミットの前にかける
