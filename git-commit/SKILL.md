# 日本語のコミットメッセージとコミットの手順

ステージング、コミットメッセージ案の作成、コミットを頼まれたときは、この手順と書式に従う。
リポジトリにコミットメッセージのテンプレートがあれば、書式はテンプレートを優先する（「リポジトリのテンプレートとの関係」の節）。

## 手順

### 1. 状態を確かめる

- `git rev-parse --is-inside-work-tree`でリポジトリかどうかを確かめる。リポジトリでなければ、その旨を伝えてから`git init -b main`で作る
- `git status --short`で変更を一覧にする

### 2. ステージする

- ステージの対象は、頼まれた作業で変えたファイルに限る。関係の無い変更が混ざっていれば、ステージせずにユーザーに伝える
- `.gitignore`のパターンが意図より広く一致していないかを確かめる。例：ビルド成果物のつもりの`app`は`cmd/app/`にも一致する。リポジトリ直下だけに一致させるときは`/app`と書く
- `git add`の出力を`Select-Object -First`や`head`に渡さない。パイプの先が途中で閉じると、`git add`も途中で止まる
- ステージしたら`git diff --cached --name-only`で、除外すべきもの（`data/`、`secrets/`、ビルド成果物、`node_modules/`、個人の設定ファイル）が入っていないことを確かめる
- ステージした差分を、秘密情報と個人情報の手がかりで検索する（トークンの接頭辞`secret_`・`ntn_`・`sk-ant`、`client_secret`、メールアドレス、カード番号、家族の氏名など）。見つかったら、ステージする前に伏せるかどうかをユーザーに確かめる
- 個人の値を含む設定ファイルは、コミットせずに見本（`<名前>.example`）を作ることを提案する。命名は`.example`が主流である（`.env.example`、`config.toml.example`）

### 3. コミットメッセージ案を作る

1. リポジトリにコミットメッセージのテンプレートが設定されているかを`git config --get commit.template`で確かめ、設定されていればそのファイルを読む（「リポジトリのテンプレートとの関係」の節）
2. 下の「書式」とテンプレートに従って、案を一時ファイル（スクラッチパッド）に`.md`で書く。コマンド、パス、エンドポイント、識別子はバッククォートで囲む（「コードの書き方」の節）。`.txt`ではバッククォートが解釈されず、textlintの自動修正から守られない
3. `japanese-tech-writing`スキルが入っていれば、その規範で点検する。入っていなくても、1つの項目に2つの事柄を詰め込んでいないか、「〜の確認」「〜の停止」のように、追加した処理なのか手で確かめたことなのかが分からない終わり方をしていないかは見る
4. プロジェクトにtextlintの設定があれば、`npx --no-install textlint --config <設定> <一時ファイル>`をかける。自動修正（`--fix`）や保存時のフックで日本語と英数字の間の空白が除かれたら、その結果を採る。ただし、自動修正がコマンドやパスの中身を変えていたら（例：`GET /v1/views`のスラッシュの前の空白を消した）、その変更は採らない。言い換えて避けることもしない。その部分をバッククォートで囲んで書き直し、もう一度かける
5. このスキルの検査スクリプトを`node "${CLAUDE_SKILL_DIR}/scripts/check_message.mjs" <ファイル>`で実行し、終了コードが0になるまで直す。テンプレートで1行目の別の桁数を決めていれば、その桁数を2つ目の引数に渡す（`node "${CLAUDE_SKILL_DIR}/scripts/check_message.mjs" <ファイル> 80`）。`${CLAUDE_SKILL_DIR}`はこのSKILL.mdのあるディレクトリを指す。Claude Code以外で展開されないときは、そのディレクトリのパスに置き換える。検査するのは次の4つ
   - 1行目の表示幅が72桁を超えていないか
   - 本文の箇条書きを折り返していないか（字下げした続きの行が無いか）
   - バッククォートの外に、HTTPのメソッドとパスがくっついた形（`GET/v1/views`）が無いか。textlintの自動修正が空白を消した跡なので、バッククォートで囲んで書き直す
   - 全角文字と、記号で始まる（または終わる）半角の語の間に空白が無いか（例：「テンプレート .gitmessage」「./internal/... の」）。textlintは半角の英数字との間しか見ないので、この形を検出しない。見つかったら空白を取るか、取ると読みにくいときは「テンプレート（.gitmessage）」のように括弧で示す
6. 案をユーザーに見せる。コードブロックに全文を入れ、書式のどこに合わせたかを短く添える。テンプレートとこのスキルの書式が食い違っていたら、その箇所とどちらに合わせたかも伝える

### 4. コミットする

- ユーザーが「コミットして」と言うまでコミットしない。案を見せたあとに修正を頼まれたら、3に戻る
- コミットは一時ファイルから`git commit --cleanup=whitespace -F <一時ファイル>`で行う。`--cleanup=whitespace`を付けないと、エディタで編集する場合と同じく`#`で始まる行（`## 問題`など）が消されることがある
- PowerShellのヒアストリングを`git commit -F -`に渡さない。標準入力にならず、メッセージが引数として解釈されて失敗する
- コミットしたら`git log --format="%h %an%n%B" -1`と`git show --stat --format="" HEAD`で、メッセージと対象のファイルを確かめて報告する
- pushはユーザーに頼まれたときだけ行う

## 書式

```
<型>: <内容を体言止めで>

## 問題
- <何が困っていたか>

## 対応
- <何をどう変えたか>

## テスト
- <どう確かめたか>

## 影響
- <既存の動作やデータへの影響、利用者に必要な作業>
```

### 1行目

- Conventional Commits（https://www.conventionalcommits.org/ja/v1.0.0/）の`<型>: <内容>`にする
- 型は`feat`（機能の追加）、`fix`（不具合の修正。計画で決めていた動作の実装漏れを含む）、`docs`、`refactor`、`test`、`chore`から選ぶ
- スコープは、変更の範囲を1つに絞れるときだけ付ける
- 内容は体言止めにする。例：`fix: 月次DBの無い月にreviewを開いたときのplan実行の案内`（`〜を案内する`で終えない）
- 表示幅72桁以内にし、折り返さない

### 本文

- 文章で書かず、節に分けた箇条書きにする。節は`## 問題`、`## 対応`、`## テスト`、`## 影響`の順で、該当しない節は省く
- 箇条書きは体言止めにする。例：「処理を追加する」ではなく「処理の追加」
- 最初のコミットのように問題が無い場合は、節を使わずに内容の一覧だけでもよい
- `Co-Authored-By`の行は付けない
- 言語は日本語

### 折り返し

- 本文は折り返さない。箇条書きの1項目を1行で書く。VS CodeやGitHubなどの画面では、長い行も自動で折り返して表示される
- 表示幅（全角2桁、半角1桁）で72桁の上限は、1行目にだけ当てる
- 1項目が長くなりすぎるときは、折り返さずに項目を2つに分ける。1つの項目に2つの事柄を入れていることが多いからである
- 目分量で決めず、`scripts/check_message.mjs`で確かめる

### コードの書き方

- コマンド（`plan --month 2026-07`）、パス（`internal/notion/view.go`）、エンドポイント（`PATCH /v1/views/{id}`）、識別子（`commit.template`）は、バッククォートで囲む
- 囲むのは、textlintの自動修正がMarkdownのインラインコードの中身を変えないからである。囲まずに書くと、`ja-no-space-around-slash`が半角どうしの間でもスラッシュの前の空白を消し、`GET /v1/views`が`GET/v1/views`になる
- 自動修正に書き換えられたときに、日本語に言い換えて避けない。書くべき内容を変えることになるので、バッククォートで囲んで元の書き方に戻す
- バッククォートと日本語の間に空白を入れない（textlintの`ja-space-around-code`に当たる）。例：`` `notion view`の追加 ``
- バッククォートは`git log`ではそのまま表示されるが、プレーンテキストでも読めるMarkdownの記法なので使ってよい

## リポジトリのテンプレートとの関係

コミットメッセージのテンプレート（`commit.template`。多くは`.gitmessage`）は、エディタでメッセージを書くときの雛形である。
このスキルは`git commit -F`でコミットするので、Gitがテンプレートの中身をメッセージに入れることは無い。
ただし書式の決まりがテンプレートとこのスキルの2か所にあるので、片方だけを直すと食い違う。そこで、次のように役割を分ける。

- 節の見出しと並びは、リポジトリのテンプレートに従う。リポジトリごとに書式を変えたいときは、テンプレートを直せば案にも反映される
- テンプレートの`#`で始まる説明の行に書かれた決まり（1行目の型、1行目の桁数、本文の折り返しなど）も、このスキルより優先する
- 手順（ステージの確認、点検、「コミットして」と言われるまで待つこと）と、テンプレートに書かれていない決まりは、このスキルに従う
- テンプレートが設定されていない、またはファイルが見つからなければ、このスキルの「書式」に従う
- テンプレートとこのスキルの書式が食い違っていたら、案を見せるときにその箇所を伝える。どちらかを直すかどうかはユーザーが決める

## コミットメッセージのテンプレートを置く

リポジトリで同じ書式を使うときは、このスキルの`${CLAUDE_SKILL_DIR}/assets/gitmessage`を`.gitmessage`として置き、`git config commit.template .gitmessage`で登録する。
エディタで`git commit`したときに、節の見出しと書式の説明が入った状態で開く。
