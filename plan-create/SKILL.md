# 実装計画（Plan）を書く

実装の前に計画を頼まれたら、この手順でPlanを書き、ファイルに残す。
Planは、実装を始める前にユーザーが内容を確かめ、必要なら`/plan-review`でCodexかClaudeにレビューさせるためのものである。

## 使う場面と使わない場面

次のように、実装の前に計画を立てるよう頼まれたときに使う。

- 「実装計画を作成して」「実装計画をしてください」「Planを書いて」
- 「設計してから実装して」

次の場合は、Planを書かずに作業を進めてよい。

- 「すぐ実装して」「Planは不要」と言われた
- 「設計してから実装して」のように計画と実装をまとめて頼まれ、変更が1ファイルの軽微な修正（typoの修正、書式の調整など）である

「Planを書いて」のように計画そのものを頼まれたときは、変更の規模によらず書く。

## 手順

1. 前提を確かめる。関係するコードや設定、既存のPlanを読む。Planの前提になる動作（コマンドの出力、ライブラリの挙動など）は、できる範囲で実行して確かめる。確かめられなかったことは、Planに「確かめていない」と書く
2. ファイルの名前を決める（「ファイルの置き場所と名前」）
3. 「Planの節の構成」に沿って書く。`japanese-tech-writing`のSkillが入っていれば、書く前に読み込み、その規範に従う
4. 書いたら、実装に進まずに止まる（「書いたあと」）

## ファイルの置き場所と名前

- 置き場所：プロジェクトのルートの`plan/`。無ければ作る
- 名前：`YYYYMMDD_<機能名>.md`（例：`20250621_user-auth.md`、`20250621_csv-import.md`）
  - 日付は今日の日付
  - 機能名は、英小文字をハイフンでつないだ短い名前（kebab-case）。英語にしにくいときは、意味の近い短い英語を選び、選んだ名前をユーザーに伝える
- 同じ名前のファイルが既にあれば、上書きしない。末尾に`-2`、`-3`を付ける（例：`20250621_user-auth-2.md`）

リポジトリのファイルを書けない環境（claude.aiの会話など）では、次のようにする。

- 同じ節の構成のPlanを、`YYYYMMDD_<機能名>.md`の名前のMarkdownのファイルとして出力する
- ファイルも出力できなければ、会話の中に全文を示す
- 既存のPlanを見られないので、名前の重複は確かめなくてよい

## Planの節の構成

次の構成で書く。当てはまらない節は省いてよく、必要なら節を足してよい。ただし「目次」「外部との入出力」「実現すること・しないこと」は省かない。

````markdown
# <機能名> 実装計画

## 目次
1. 問題と対応方針
2. 実装範囲
3. …（書いた節を、書いた順に並べる）

## 問題と対応方針
- 問題：…
- 対応方針：…（1文目に方針、2文目以降に対応の概略）

## 実装範囲
- 実装するもの
  - …
- 実装しないもの
  - …

## 外部との入出力
- 読み書きするもの：…
- 読み書きしないもの：…

## 実現すること・しないこと
- 実現すること：
  - …
- 実現しないこと：
  - …（理由）

## 技術選定・前提
- 使う言語・フレームワーク・ライブラリ
- 既存のコードとの整合性
- 確かめた前提と、確かめていない前提

## 変更前後の構成

### 変更前
```text
…
```

### 変更後
```text
…
```

### 変わる点
- …

## 実装ステップ
1. …

## 変更するファイル
- …

## エラーハンドリング・エッジケース
- 想定される失敗と、その対処

## テスト方針
- どのレベルでテストするか
- 確かめるケース

## 懸念事項
- この実装の外への影響
  - …
- あえて扱わないこと
  - …（理由）

## 実装時に決める事項
- Planで決めなくても、実装とテストで決められる事項（1行ずつ）

## 未確定事項・要確認
- 仕様の曖昧な点
- ユーザーに確かめたい点
````

### 目次（必須）

- 先頭の見出しの直後に置き、書いた節の名前を、書いた順に番号付きの箇条書きで並べる。「目次」自体は並べない
- 節へのリンクは付けない。見出しの「・」などからリンク先を作る方法がビューアによって違い、リンクが切れるおそれがある
- 節を足したり省いたりしたら、目次も直す

### 問題と対応方針

- 問題：今の状態と、それで困ること
- 対応方針：1文目に方針として、何を優先し、そのために何を受け入れるかを書く。2文目以降に、対応の概略を1〜2文で書く。詳しいことは、「実装範囲」より後の節に書く

対応方針の例を示す。

```markdown
- 対応方針：アップロードの応答時間を短くすることを優先し、サムネイルができるまでの遅れは受け入れる。サムネイルの生成をワーカーに移し、アップロードの応答は元の画像を保存した時点で返す
```

方針で受け入れたことは、「実現しないこと」の理由として書く。例「サムネイルができるまでの時間の上限（理由：対応方針のとおり、サムネイルの遅れは受け入れる）」。

### 外部との入出力と、実現すること・しないこと（必須）

この2つの節で、レビューでどこまでの穴を指摘するかが決まる。節が無いと、考えうるすべての穴が指摘され、レビューが終わらなくなる。`/plan-review`もこの2つの節を前提にしている。

2つの節には、次の4点を書く。

- 読み書きするもの：実装したものが読み書きする外部のもの（ファイル、DB、外部のAPI・サービス、接続先のLLMなど）。「外部との入出力」に書く。例「ローカルのファイルと、接続先のLLMのAPIだけ」「GitHubのAPIでIssueを読み、PRを作る」
- 読み書きしないもの：触れないことを示しておく外部のもの。「外部との入出力」に書く。例「ほかの外部サービスは読み書きしない」
- 実現すること：実装によって成り立つ状態を、3〜5個に絞って挙げる。「実現すること・しないこと」に書く。失敗したときに成り立つこと（例「失敗しても元のデータは残り、〜で作り直せる」）もここに書く
- 実現しないこと：意図して実現しない状態と、その理由。「実現すること・しないこと」に書く。例「電源断でも書きかけのファイルが壊れないこと（理由：〜）」「対象のツール以外のプロセスが書き換えても壊れないこと（理由：〜）」

次の項目は、当てはまるときだけ「外部との入出力」に書く。

- 同時に使う人・LLM：複数の人やLLMが、同じPlanやデータを同時に読み書きする場合に、その形を書く。書かなければ、1人が1つのセッションで使うものとして扱う

「実現すること」と「実現しないこと」は、近い節と次のように書き分ける。

- 「実装範囲」には、作るもの（機能や部品）を書く。「実現すること」には、作ったものによって成り立つ状態を、「〜は〜する」「〜は〜になる」の形で書く。例「`POST /images`からサムネイルの生成を外す」は実装範囲、「アップロードの応答は、サムネイルの生成を待たずに返る」は実現すること
- 「実現しないこと」には、実現しなくても困らないものだけを書く。困るおそれはあるが、この計画では扱わないものは、「懸念事項」の「あえて扱わないこと」に書く

「問題と対応方針」から書き起こし、頼まれていないことは「実現すること」に足さない。実現することを多く見積もりすぎると、レビューの指摘が尽きなくなる。

### 変更前後の構成

構成（部品と、部品の間のデータの流れ）が変わるときに書く。構成が変わらない変更（1つの関数の中の修正など）では省く。

- 変更前と変更後の図を、`text`のコードブロックに、ASCIIの文字で描く。Mermaidは使わない
- 変更前の図は、手順1で読んだコードと設定をもとに描く
- 線と矢印は、ASCIIの`|`、`-`、`+`、`>`、`v`だけで描く。罫線の文字（`─`、`│`など）は、環境によって幅が変わり、図がずれる
- 日本語より右に、位置をそろえる線や枠を置かない。日本語の文字の幅も、環境によって変わる。部品を枠で囲まず、枝分かれは左から木の形で描く
- 変更後の図では、足す部品に（新規）、変える部品に（変更）を付ける。なくなる部品は、変更前の図で（削除）を付ける
- 図の下の「変わる点」に、図から読み取ってほしい変化を箇条書きで書く

変更後の図の例を示す。

```text
クライアント
  |
  | POST /images
  v
APIサーバー（変更）
  |-- 元の画像 --> オブジェクトストレージ
  +-- 画像の行とジョブの行 --> DB：images（変更）、jobs

DB：jobs
  |
  | ジョブを取り出す
  v
ワーカー（変更）
  +-- サムネイルの生成のジョブ（新規）
        |-- サムネイル --> オブジェクトストレージ
        +-- thumbnail_statusの更新 --> DB：images
```

### 懸念事項（任意）

この計画の外に及ぶことを書く。当てはまらなければ省く。

- この実装の外への影響：画面、ほかのコンポーネント、運用・事務など、変更するファイルの外で、動きや作業が変わるもの
- あえて扱わないこと：困るおそれはあるが、大きすぎるなどの理由で、この計画では扱わないことと、その理由（例「別の計画で扱う」）

`/plan-review`の指摘のうち、この計画で扱うには大きすぎるものの足し先にもなる。

### 実装時に決める事項（任意）

Planで決めなくても、実装とテストで決められる事項を1行ずつ書く。`/plan-review`の指摘のうち、実装で決めれば足りるものの足し先にもなる。

## 書いたあと

- 実装に進まない。ユーザーが内容を確かめ、必要なら`/plan-review`でレビューすることを想定している。「実装して」と明示的に言われるまで待つ
- 作ったファイルのパスと、`/plan-review`でレビューできることを伝える。`/plan-review`はClaude Code（手元かクラウドセッション）が前提なので、ファイルを書けない環境で出力したときは、リポジトリの`plan/`に置けばレビューできると伝える
- 「懸念事項」と「未確定事項・要確認」があれば、その要点も伝える
