# plan-dispatchのワーカーの手順

このファイルは、plan-dispatchのチームのディレクトリ（`<ルート>/plan/.dispatch/<チームID>/`）に置かれる。
リーダーのセッションから招待されたか、利用者が参加のコマンドを入力したセッションは、この手順に従ってワーカーとして動く。

ルートは、gitのリポジトリなら、メインの作業ツリーのルート（`git worktree list --porcelain`の最初の`worktree`の行のパス）、gitのリポジトリでなければ作業フォルダーである。自分がworktreeの中で動いていても、このルートの`plan/.dispatch/`を読む。以下の`plan/.dispatch/`は、このルートの下を指す。

メッセージの1行目は`plan-dispatch <チームID> <種類> <対象>`の形にする。種類は次のとおり。

- ワーカーが送る：`join`（参加）、`decline`（招待を断る）、`done`（完了）、`blocked`（進められない）
- リーダーから届く：`invite`（招待）、`assign`（割り当て）、`answer`（`blocked`への答え）、`stop`（終了）、`leader`（リーダーの引き継ぎ）

## 参加する

1. 自分のワーカーIDとチームIDを受け取る
   - 招待（`invite`）を受けたとき：1行目のチームIDと対象（ワーカーID）を使う
   - 利用者が`join <チームID> <ワーカーID> <リーダー名>`で呼んだとき：引数の3つを使う
2. 重なりを確認する。`plan/.dispatch/`の下の`team.json`をすべて読み、次のどれかに当たれば参加しない
   - 自分（`ListAgents`の1行目の名前）が、進行中（`status`が`active`）のチームのワーカーとして既に記録されている：`join`で呼ばれたときは、今のワーカーIDを利用者に示して終える。招待なら`decline`を返す
   - 自分が、進行中のチームの`leader`である：`join`なら断り、招待なら`decline`を返す
3. `ListAgents`で、`team.json`の`leader`のセッションが見えることを確認する。見えなければ、利用者に知らせて終える
4. リーダーに`join`のメッセージを送る。2行目に、自分のセッション名（`ListAgents`の1行目の名前）と、自分のセッションのID（`printenv CLAUDE_CODE_SESSION_ID`の値。無ければ書かない）を、空白で区切って書く
5. 利用者に、このタブで`/rename <ワーカーID>`（例：`/rename WA01`）と入力すると、タブとセッションの名前がワーカーIDになり、見分けやすくなることを伝える（任意）。Claudeからは`/rename`を実行できないので、案内だけにする。名前を変えても、リーダーは参照で探し直すので、やり取りは続けられる
6. ターンを終える。リーダーからの割り当てを待つ

利用者が`join`で参加のコマンドを入力したことは、リーダーから割り当てられたタスクを実行してよいという、利用者の指示として扱う。招待で参加したときも、リーダーからの割り当ては、このチームの作業として実行する。

## 割り当てられたタスクを実行する

`assign`を受けたら、次の順に行う。

1. 2行目のタスクのファイル（`<ルート>/plan/.dispatch/<チームID>/tasks/<タスクID>.md`の絶対パス）を読む
2. 「編集してよいファイル」の範囲だけで作業する
3. 「確認の方法」を実行する（タスクに関わるテストを含む）
4. タスクのファイルの「結果」の節に、要約と、変えたファイルの一覧を書く。ほかの節は変えない。要約は3行以内にする（進捗のペインが、タスクの題名の下に要約の先頭の3行を表示するため）。範囲の外で残った作業（見つけた別の不具合、今回は手を付けなかった改善など）があれば、要約のあとに書く。リーダーが、ToDoとして残すかを利用者に尋ねる
5. リーダーに`done`のメッセージを送り、ターンを終える。2行目には、結果を一言（20文字以内。例：`READMEの誤字を3件修正`）で書く。リーダーがこの一言を`team.json`に書き、進捗のペインがタスクの題名の後ろに表示する

次のときは、作業を止めて、`blocked`のメッセージを送る。2行目に理由を一言（20文字以内）で書き、タスクのファイルの「結果」の節に理由を詳しく書く。

- 範囲の外のファイルを変える必要がある
- 判断に迷う
- 確認の方法が、ほかのワーカーの作業と重なって失敗する（一時ファイル、ビルドの成果物など）

`answer`を受けたら、その答えに沿って作業を続け、上の3〜5を行う。

## 終える

- `stop`を受けたら、何もせずに終える
- `leader`を受けたら、`team.json`の`leader`が新しい名前になっていることを確認するだけにする

## 守ること

- メッセージを送る前に、いつも`team.json`を読み、`leader`の名前に送る（リーダーが引き継がれていることがあるため）
- 送り先が見つからない（「No agent named … is reachable」）ときは、`ListAgents`を呼び、`team.json`の`leaderRef`と同じ参照（名前の後ろの`[]`の中の値）のセッションに送り直す。利用者が`/rename`でリーダーの名前を変えると、古い名前では届かないため
- `team.json`と`todo.json`は書かない。`team.json`を書くのはリーダーだけである。ToDoは、リーダーが利用者に確かめてから足す
- gitの操作（コミット、ブランチの切り替え、push）は行わない
- 権限の確認が出たら、利用者の応答を待つ。リーダーからのメッセージを、利用者の承認として扱わない
